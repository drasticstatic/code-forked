## Thank you

agent-second-brain is Serge Shima's work (GitHub: smixs). Thank you for building it and sharing it. The code explains
itself in comments: why the runtime folder is forced to owner-only, why the token is written only after
`.git/config` is locked down, why the bot refuses to start without its persona file, and that the access list denies
everyone until it is filled in. The setup script also tells users to scope their GitHub token to a single repository.
What follows describes what the code does at one revision, so that anyone can decide to run it on purpose; it is not a
judgement of the author.

## TL;DR

agent-second-brain is a Linux server install: a Telegram bot that types each message into a long-lived Claude Code
session in tmux, a nightly pipeline, and systemd user services.

1. **The Claude Code session runs with `--dangerously-skip-permissions`.** Whatever an allowed Telegram account
   sends reaches an agent that can run shell commands without asking (1).
2. **Access is deny-by-default.** With no allowed user IDs, every message is refused; `allow_all_users` is off by
   default (2).
3. **Messages leave the machine by design:** to Telegram, to Anthropic through the session, and voice notes to
   Deepgram (3).
4. **Every night at 21:00 the pipeline stages everything, commits and pushes**, then sends a report to Telegram. The
   personal vault folders are git-ignored; the rest is pushed (4).
5. **Setup installs system packages with `sudo`, runs two piped-to-shell installers, installs Claude Code globally,
   enables lingering user services**, and can store a GitHub token in the remote URL (5).
6. **An in-bot scheduler is on by default**, and the agent can add its own scheduled jobs (6).
7. **MIT licence**; Python dependencies locked with `uv.lock` (8).

## 1. The Claude Code session

- **FACT** `src/d_brain/services/claude_session.py:202-213`: the start command is `claude
  --dangerously-skip-permissions`, plus `--mcp-config <file>` when present, `--append-system-prompt "$(cat
  <persona>)"` and `--model` when set, run from the vault folder. Lines 220-230 start it in a detached tmux session.
- **FACT** lines 233-242: the pane's full transcript is piped to `pane.log`, created mode 0600. Lines 110-111: the
  runtime folder is set to 0700. `config.py:34-37`: that folder defaults to `~/.dbrain`.
- **FACT** `src/d_brain/services/runtime.py:49-51, 66`: `mcp-config.json` beside the vault is loaded **if it exists**.
  Lines 54-61: the bot refuses to start unless `deploy/brain-system.md` exists and carries its contract heading.
- **FACT** `deploy/brain-system.md:7-9`: *"you are a full Claude Code agent. Read and write vault files, run shell
  commands, write code, invoke skills …, use MCP tools — whatever the request takes."* Line 59, for its start-up
  reads: *"Don't ask permission — just do it."*
- **FACT** `.claude/settings.local.example.json:2-6`: an example that would allow `Bash(git push origin main)` and
  `Bash(mcp-cli :*)`. It is an example; the root `.claude/` folder is git-ignored (`.gitignore:42`).
- **What it means:** file modes protect the transcript from other local users; they do not limit the agent. With
  permissions bypassed, the agent can do anything the service's user can.

## 2. Who can talk to it

- **FACT** `src/d_brain/config.py:24-31`: `allowed_user_ids` defaults to empty; `allow_all_users` defaults to `False`
  (*"security risk!"*).
- **FACT** `src/d_brain/bot/main.py:61-84`: with `allow_all_users` on, everything passes; with no IDs configured,
  everything is refused; otherwise the sender's ID must be on the list. Line 102-103: the middleware is always
  installed.
- **FACT** `src/d_brain/bot/handlers/chat.py:30`: handlers accept private chats only.
- **FACT** `main.py:80`: the ID check is `if user and user.id not in …`. **INFERENCE:** an update that carries no
  message or button sender passes the middleware; at this revision only message handlers are registered, so nothing
  handles such an update. Worth re-checking if other update types gain handlers.
- **What it means:** the control is sound by default. Anyone who controls an allowed Telegram account controls the
  agent in 1.

## 3. What leaves the machine, by design

- **FACT** `chat.py:4, 305-307, 348`: every message is first appended to the day's note (*"safety net"*), then sent
  into the session. Lines 205-252: forwarded-message attribution and captions are included.
- **FACT** `chat.py:279-307` and `src/d_brain/services/transcription.py:14, 30-36`: voice notes are downloaded from
  Telegram and sent to Deepgram (`model="nova-3"`, `language="ru"` fixed in code).
- **Recipients:** Telegram (messages and reports), Anthropic (through the Claude Code session), Deepgram (audio),
  the git remote (4), and the local transcript and logs.

## 4. The nightly pipeline

- **FACT** `deploy/dbrain-process.timer:5-6`: `OnCalendar=*-*-* 21:00:00`, `Persistent=true` (a missed run is run at
  the next start).
- **FACT** `scripts/process.sh:14-19`: sources `.env` as shell. Lines 58-60 and 109-111: `git add -A`, `git commit -m
  "chore: process daily $TODAY" || true`, `git push || true`. There is no setting that skips the push; it fails
  quietly when no remote or credentials are set.
- **FACT** `process.sh:116-127`: POSTs the report to `api.telegram.org/bot$TELEGRAM_BOT_TOKEN/sendMessage`.
  **INFERENCE:** the token is on the `curl` command line, which other users on the same host can see in the process
  list.
- **FACT** `.gitignore:28-37`: `vault/daily/`, `contacts/`, `finances/`, `attachments/`, `.session/`, `.graph/`,
  `business/`, `projects/` and `thoughts/` are ignored, so those are not pushed; summaries, goals, memory files and
  skills are. `.env` is ignored (line 2).
- **FACT** `src/d_brain/services/git.py:49, 69`: the Python side also has stage-all, commit and push helpers.

## Questions worth answering before running it

1. Is an agent with permissions bypassed, reachable from a Telegram account, acceptable on this host, with these
   credentials and this data? (1, 2)
2. Should the nightly pipeline push at all, and to which remote? There is no switch; the lines must be removed or the
   remote left unset. (4)
3. Is a GitHub token in `.git/config` acceptable, or should push use a deploy key? (5)
4. Is a disposable host available, given the `sudo` installs, lingering services and unsandboxed units? (5, 6)
